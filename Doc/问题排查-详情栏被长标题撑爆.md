# 问题排查经验：详情栏被 nowrap 长标题撑爆（右侧内容被裁、窗格无法拖回，v0.5.2）

> 记录时间：2026-08-17
> 影响版本：v0.5.2（`0c1227b` 修复）
> 修复提交：`0c1227b`（main，含两个回归测试）
> 根因类别：Zotero 9 `item-pane` 的 Gecko flex `min-content` 宽度传播
> 关联文档：[`PLAN.md`](./PLAN.md)（§9 区块）、[`Zotero9-阅读器插件开发方法.md`](./Zotero9-阅读器插件开发方法.md)

---

## 1. 问题概述

**现象**：输入/渲染翻译文本后，Zotero **内容窗格（右侧详情栏 / item-pane）出现严重宽度异常**——右侧内容被整段裁掉，且**无法拖回恢复**。出现在历史区、结果卡片、阅读器侧栏等所有渲染长文本的区域。

**两种典型形态**（我方截图坐标分析）：

- **窄窗口**（item-pane 可视 ~357px）：被裁 ~656px，几乎只能看到每行最左一小段。
- **较宽窗口**（item-pane 可视 ~890px）：每行在 ~983px 宽度排版、右缘 ~90px 被挤出可视区，句子尾部"消失"（例：`利用第一性原理计算…热力学性质以及B1 (`、`对于地球物理学中` —— 括号/句子没写完）。

**前一轮误判**：曾以为是历史预览 `-webkit-box/-webkit-line-clamp` 的多行折叠空洞（"只见首尾片段"），并据此改了一次 CSS。用户重装后**无效**，才意识到真正机制是容器级横向撑爆，不是丢行。

---

## 2. 根因分析（证据链）

### 2.1 决定性复现（Gecko harness 实测）

在隔离的 Zotero 9.0.6 集成测试环境里，用**真实故障数据**（`translation_history` id=27，item 4921 的 NaCl 译文 + 英文标题）构造区块历史条目，测量各容器宽度：

```
修复前：
  item-pane:  clientW=357, scrollW=1013   ← 可视 357px，内容被撑到 1013px，右侧 656px 被裁
  body:       cw=997,    sw=999            ← 区块 body 被撑到 ~1000px
  .ztr-history-source: cw=983, sw=983      ← nowrap 英文标题（111字符≈983px）—— 元凶
```

`scrollWidth(1013) - clientWidth(357) = 656px`——这就是用户看到的"右侧内容整段被裁、窗格卡住"。

### 2.2 机制：Gecko flex `min-content` 宽度传播

历史条目的 `.ztr-history-source`（蓝色英文标题）设了 `white-space: nowrap`（产品意图：单行 + 省略号）。但：

- Zotero 9 强制自定义区块 body 为 `display:flex; flex-direction:column`（`content/zotero-platform/mac/zotero.css` 里 `item-pane-custom-section .body`）。
- flex 布局中，首行 `nowrap` 内容的**最大内容宽度（max-content ≈ 983px）**沿 flex 链逐级向上传播：`.ztr-section` → `.body` → `item-pane-custom-section` → `.zotero-item-pane-content`（`flex:1; min-width:auto`）→ `item-pane`。
- 结果：`item-pane` 的内容区被撑到 ~1013px，而主窗口 flex 只分给它 357px（或用户手动拖到 890px）可视宽度 → **右缘溢出被裁**；因 `min-content` 锁定了最小宽度，splitter 拖不动、窗格无法恢复。

**关键点：`max-width:100%` 无法阻止该传播**。在 Gecko 的 intrinsic 尺寸计算里，flex 子项的百分比 `max-width` 处于"父宽度未知"的循环场景，规范按 `auto`（不约束）处理，因此 `nowrap` 内容的整行宽度仍被计入 min-content。

### 2.3 为什么 Chrome 不复发（Blink vs Gecko）

同一份 DOM + CSS 在 Chromium(Edge) headless 里测：`host.scrollWidth=400 = clientWidth=400`，**不撑爆**。Gecko 对 flex item 的 intrinsic `min-width` 计算与 Blink 存在差异，导致 `nowrap` 内容在 Gecko 里成为撑爆源头。结论：**该问题仅在 Gecko（Zotero）出现，Blink 无法在浏览器复现，必须用真实 Zotero 集成测试来锁测。**

## 3. 修复方案

### 3.1 CSS 修复（`addon/content/zoteroPane.css`）

给区块根 `.ztr-section` 增加 **CSS containment**，切断内容宽度向内联尺寸的传播：

```css
.ztr-section {
  display: flex;
  flex-direction: column;
  gap: 8px;
  padding: 4px 0;
  font-size: 12px;
  color: var(--fill-primary, #333);
  box-sizing: border-box;
  /* 隔离内容宽度向内联尺寸的传播：
     区块内的 nowrap 长内容（如英文标题 .ztr-history-source）会经 Gecko flex
     min-content 链（body → custom-section → item-pane-content → item-pane）
     把整个右侧详情栏撑爆。contain:inline-size 让本区块宽度只由父容器决定；
     min-width:0/width:100% 允许在父 flex 中正常收缩。 */
  min-width: 0;
  width: 100%;
  max-width: 100%;
  contain: inline-size;
}
```

另外给 flex 行容器 `.ztr-toolbar`、`.ztr-history-head` 补 `min-width:0`，消除同类传播隐患。

顺带把 `.ztr-history-preview` 由 `-webkit-box/-webkit-line-clamp` 改为**块级 `max-height` 折叠**（移除 Gecko 脆弱路径）：

```css
.ztr-history-preview {
  ...
  display: block;
  max-height: calc(12px * 1.4 * 3); /* 3 行 */
  overflow: hidden;
}
.ztr-history-item.expanded .ztr-history-preview {
  max-height: none;
  overflow: visible;
}
```

> 说明：前一轮误判曾把成因归给 `-webkit-box`，本提交仍保留该块级化改动（无害且从源头排除一条 Gecko 脆弱路径），但**真正的撑爆修复是 `contain:inline-size`**。

### 3.2 验证结果（harness 实测）

```
修复后：
  item-pane:  cw=357, sw=357   ✅ 不再溢出
  body:       cw=304, sw=304   ✅ 不再溢出
  .ztr-history-source: cw=290, sw=983  ← 标题内容仍 983，但被裁剪为省略号(…)，不再撑父容器
```

全套 **82 个测试通过**，用户重装确认**修复生效**。

## 4. 排查过程（方法学）

### 4.1 定位路径（弯路 → 正路）

1. **像素级分析截图**：老截图窄窗、文本每行右缘不一致（x≈517/547/931/959），误判为"丢中间行"。
2. **盲信 Chrome 复现**：在 Chromium 里同样 DOM 不复发 → 误判为 `-webkit-box` 空洞 → 改了一次无效。
3. **对比第二张更宽的截图**：发现**整个 item-pane 撑满窗口**、PDF 视图被挤成 80px 细条——转向"容器被撑宽"方向。
4. **在真实 Zotero harness 里量 scrollWidth**：才拿到 `pane.sw=1013 vs cw=357` 的决定性数字。**Chrome 测不出来，必须用 Gecko。**

### 4.2 关键技巧

- **测容器溢出要量 `scrollWidth` vs `clientWidth`，而不是只盯文本是否换行**。此前测试一直断言"文本无空洞/正常换行"，全部通过，掩盖了真正的容器级撑爆。
- **同一个故障别急着改**：第一次只改了症状层（line-clamp），用户反馈无效后才挖到机制层（flex min-content 传播）。先确认红灯复现，再动手。
- **Blink 与 Gecko 的 flex intrinsic 计算不一致**：UI 布局 bug 用浏览器(Edge/Chrome)复现可能"恰好正常"，必须用与 Zotero 同内核的环境锁测。

## 5. 沉淀：Zotero 9 自定义区块布局要点

- **Zotero 9 强制 `.body { display:flex; flex-direction:column }`**（`item-pane-custom-section .body`）。
- flex 块容器的宽度默认取**内容 max-content**；子项 `nowrap` 长内容会让 max-content 被撑到超长，并经 flex 链传到 `item-pane`。
- 插件区块根必须**显式隔离宽度**：`contain: inline-size`（或等价手段）是最干净的解；`max-width:100%` 在 Gecko intrinsic 计算里不约束 norap 内容，**不够用**。
- flex 行容器（toolbar / head 等）默认 `min-width:auto`，同样可能被 nowrap 子项撑宽，需一并 `min-width:0`。

---

## 6. 预防措施（防再犯）

1. **任何会把长内容放进区块的文案**（英文标题、URL、DOI、密钥）都不裸 `nowrap`，且其直系 flex 容器要有 `min-width:0`；区块根 `.ztr-section` 的 `contain:inline-size` 已足矣，但新增区块类型时持续核对。
2. **新增两个回归测试**（已在 `test/`）：
   - `repro-overflow.test.ts`：item-pane / body 不得横向溢出（直接锁住"被撑爆"）。
   - `render-preview.test.ts`：窄车道折叠→展开后长段落全文无布局空洞。
3. 布局类 bug 的修复必须**在真实 Zotero(Gecko) 集成测试里跑红→绿**，Chrome 通过不算数。
4. 用户报"窗口被撑/拖不回"类问题时，优先怀疑**容器宽度被内容 max-content 撑爆**，而非逐字排查文本内容。
